## The common/extension boundary

| Classification | Meaning | Examples |
|---|---|---|
| Shared service | One owner and implementation serving every supported game and mixed recipe. | File storage, renderer submission, audio device/mixer, input devices, download scheduling, console discovery, save coordination. |
| Compatibility adapter | Translates an external format or contract without creating another engine. Usually selected from the asset, peer, or guest rather than a menu preference. | BSP/MDL/MD2/MD3 readers, network packet formats, demo codecs, QuakeC/QVM host services, source cvar names/flags. |
| Selectable behavior | A gameplay or presentation policy whose differences are intentional. Uses the same engine services. | Movement, character, weapons, monsters, pickups, grapple mode, offhand grenades, and source presentation. |
| Map-owned behavior | Authored logic retained with the selected world/campaign. | Target graphs, doors, lava, jump pads, boss triggers, exits, and progression. Surgical replacement of map internals is outside the current selection scope. |

Game modes remain an independent rules selection. A campaign belongs with its maps and progression. A protocol choice does not become the choice of a separate rendering, audio, input, or download engine. Connecting to a native server preserves the server's protocol and authoritative rules; locally selectable presentation cannot override those rules.

“Best implementation” means the best shared implementation that retains the required feature union and observable behavior. Newest source alone is not a selection criterion. For each consolidation, compare source algorithms, features, error behavior, numerical requirements, runtime cost, and the real callers. Keep a specialized algorithm where source compatibility requires it; share its surrounding ownership, resources, and operations. Do not reduce the common service to the lowest common denominator.

## Common quality gates

These apply to every target and add work beyond the historical requirement denominator. For each implementation unit, select focused checks proportional to the behavior it changes. Prioritize working features and measured performance; live playthrough feedback will change the code and tests, with fuller hardening afterward. The workload and comparison tables identify relevant evidence, not an exhaustive all-matrix gate on every change. Quality and native compatibility requirements remain in force, and unchecked paths remain open.

1. **Correctness:** Compare source-observable behavior and real callers. Retain native numerical/order constraints where required. One shared interface over three untouched independent engines does not count as consolidation.
2. **Mixed composition:** Exercise the target with independently selected world/campaign, movement, character, weapons, monsters, pickups, and equipment. Preserve explicit selections through travel, save, and UI configuration.
3. **Performance:** Treat frame time, responsiveness, memory, and loading cost as primary acceptance criteria for every subsystem. Follow the [performance and fidelity contract](performance.md): compare identical simulation work and inputs, measure tail latency and resource growth, and verify unchanged required visual, audio, gameplay, and protocol behavior. Keep diagnostic overhead separate from timing. Accept only demonstrated benefits; reduced quality does not qualify as an engine optimization.
4. **Failure and lifecycle:** Cancel or fail initialization, download, guest creation, media, and save operations. Retained sessions and profiles remain coherent. Release resources and held actions exactly once.
5. **User flow:** Verify the normal menu/console/keyboard/controller path, useful error text, current values, and persistence. Registration and unit tests alone do not complete the feature.
6. **Native compatibility:** When a target affects networking, files, or gamecode, qualify the required native peers/formats/modules in addition to the shared internal tests.
7. **Delivery:** Record exact source and executable hashes, inspect the built artifact, and identify installed versus unshipped changes. Platform claims require native evidence for this engine. CI and releases remain outside the currently authorized work.

The frame-time budget and reference workload should be explicit before a performance target is closed. The earlier isolated mixed route measured about 14 FPS; current installed FPS remains unqualified, so performance is still open. No broad acceptance follows from a short successful session.

## How a target is evaluated

For each source requirement assigned to a target, record: the exact remaining behavior, the chosen common owner, any preserved adapter/policy, source evidence, current implementation, public workflow, acceptance case, and result. Completion requires the remaining behavior and its callers to pass. A supporting module is recorded as a prerequisite until its public workflow is joined.

Historical open reasons that say no browser, no QVM execution, no configuration persistence, no Q3 saves, or no Team Arena progression must first be reconciled with later accepted work. Reuse those accepted implementations. Do not rebuild them from an obsolete sentence, and do not close the broader requirement merely because one constituent now works.
