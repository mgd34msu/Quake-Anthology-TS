# Team Arena interchangeability backend design

Read-only inspection of canonical .artifacts/resume-20260917/t10-combined/source. No live runtime.ts read or edited, no compiler/tests/native execution. Startup selection remains owned by weapon_binding_defaults. The two directions have different missing services and should be verified as separate units.

## Team Arena map with a selected Q1 or Q2 arsenal

runtime.ts:createSelectedQ1Arsenal and createSelectedQ2Arsenal reject source.game.options.product === missionpack. Existing selected Q1/Q2 construction, mission weapon registration, shared inventory, weapon callbacks and save/restore already cover Q3 source maps. The guard is broader than the actual supply gap.

The real supply gaps are concrete:

- expansion-source-supply.ts aliases Q1/Q2 expansion pickups but has no Q3 nailgun, chaingun or proxlauncher source aliases, for either weapons or ammo.
- runtime.ts:selectedQ3Supply recognizes all three weapon tags through q3WeaponItem, but looks up weapon-ammo quantity against the hardcoded Q3_Q1_SUPPLY_PROFILE or Q3_Q2_SUPPLY_PROFILE. Those profiles contain base Q3 rows only. Therefore Team Arena weapon pickups are rejected even if admission separately gains aliases. Ammo offers reach admission but currently have no mapping there.
- giveSelectedItem separately chooses the same base profiles, so console grants can diverge from pickup admission. The Hipnotic special profile is another reason to use the actual selected profile rather than reconstructing one from family.

Small generalized fix: retain the resolved PickupSupplyProfile beside selectedSupply, and make pickup quantity, preview, admission and source-name console lookup share that exact object. Add explicit Team Arena source aliases to expansionSourceSupply: nailgun/chaingun derive from the machinegun group and proxlauncher from the grenade-launcher group, for both ownership and ammo. This follows the existing documented expansion-source policy and needs review as a deliberate composition mapping. Keep source quantities, dropped-weapon rules, destination capacities, selection policy and respawn timing unchanged. Apply aliases after destination expansion, so TA pickups can feed selected Hipnotic/Rogue/Xatrix weapons through the existing resolved destination groups. Remove each guard only after these paths work.

Primary supply ownership: src/content/composition/expansion-source-supply.ts and src/app/bootstrap/simulation/runtime.ts; existing tests/composition/q3-q2-supply.test.ts and q1-supply.test.ts. Runtime ownership is required before implementation and must use an isolated canonical snapshot. No startup-selection.ts change belongs here. Q3_Q1/Q3_Q2 profile definitions need not duplicate expansion rows if all consumers use the resolved profile.

Holdables already have a native owner in this direction. runtime.ts:2678-2687 calls source.game.stepHoldable before selected primary stepping, including primary-command blocking. Native Team Arena client-events.ts implements kamikaze, portal and invulnerability, and ordinary teleporter/medkit. Retain these native services and their source save state. Do not route them into the foreign Q3 holdable throw.

Persistent powerups need explicit completion evidence before claiming all supplies interchangeable. team-arena/client-effects.ts:150-160 regenerates only native ps.ammo weapon slots using source ammoTimes. Q1/Q2 selected arsenals spend SharedInventoryTable entries, so that loop does not inherently refill their active pools. A generalized adapter should route source regeneration receipts through the same resolved supply destinations, retaining source timing and preventing duplicate grants when several source pools map to one destination. This requires an explicit aggregation policy and source callback, not repeated pickup side effects. Scout/ammo-regen fire-rate modifiers in movement/q3/weapon.ts:136-138 are Q3 weapon rules; selected Q1/Q2 weapons have their own clocks. Do not silently apply or promise those modifiers without defining cross-provider effect ownership. Guard/health and combat powerups remain native source state, but their interactions need focused verification.

Save implications for the supply-only unit: resolved profile is deterministic from the recipe, not a new independent save authority. Q1/Q2 selected weapon checkpoints and mission callback identities already exist. Preserve old base profile identities/compatibility where practical; do not retroactively reject old saves merely because the lookup now stores the resolved object. If regen adaptation creates extra scheduling state, serialize that state or keep authoritative timing in the existing source client ammoTimes. Pickup state, grant capacities and selected active weapon must survive save/restore and campaign travel.

## Team Arena arsenal on a Q1/Q2 or different Q3 source product

This is not a supply-only guard removal. runtime.ts:523 rejects any selected foreign Q3 arsenal on a Q3 source; line525 rejects missionpack on foreign Q1/Q2 sources. Construction below forces product baseq3 and a baseq3 spawn loadout. The same-family product difference needs a real selected-arsenal path instead of assuming source.kind q3 means the native source arsenal is sufficient.

Catalog infrastructure already exists. content/q3/foundation/arsenal.ts defines weapons11/12/13 and their inventory IDs. Q3SelectedArsenal already accepts missionpack, configures product-filtered inventory, selection, HUD and model paths, and checkpoints runtime.product plus holdable/persistent tags. Extend expansion-supply.ts with a reviewed q3-missionpack destination group so source supplies grant and replenish the three expansion weapons instead of merely changing the product flag. Existing base behavior must remain the same.

The shared firing adapter is incomplete. q3-ballistics.ts supports nailgun11 and chaingun13, but weapon12 falls through to an error. Bullet/contact contexts hardcode product baseq3, and its projectile host has no Team Arena special/reflection behavior. Q3ProjectileState retains only flight/event, not mine arming, attachment, trigger and explosion states. Existing base/game/missile.ts has authoritative proximity behavior, scheduled think/touch/die callbacks, team filtering, player attachment/stacking, mover interaction and invulnerability effects. Those services depend on native GameEntity, GameClient, entity pools and combat context, so a fabricated source entity is not an acceptable shortcut.

Minimal generalized ballistic boundary: reuse existing Q3ProjectileHost.special/reflection ports and extract the proximity state transitions from MissileRuntime behind actor/body/combat/time/event ports, then adapt both native MissileRuntime and Q3SharedBallistics to that one implementation. Preserve source numeric/time/random behavior, ownership, damage provenance and callback lifetimes. Generalizing this is a separate bounded implementation unit from supply translation; it should not be hidden inside runtime.ts construction.

Likely ballistic ownership: app/bootstrap/simulation/q3-ballistics.ts; content/q3/base/game/missile.ts and projectile.ts if the current host needs extension; a focused shared proximity module if extraction keeps those files smaller. Existing projectile/missionpack tests should validate the extraction before a foreign-world integration test. Direct nails/chaingun must also get product-correct invulnerability/reflection paths, not only avoid the weapon12 exception.

Holdable and persistent state has another owner gap. The foreign constructor supplies useHoldable that always throws. Q3SelectedArsenal spawns holdable/persistent tags as zero and has no authoritative pickup/update service to populate them. Native client-events.ts handlers require source spawn selection, teleport, item drops, Team Arena objectives, portal and kamikaze services. Complete selected Team Arena equipment needs a typed session adapter for these effects plus actor-owned holdable/persistent state. Keep map-source objectives and spawn authority separate from arsenal provider. Portal destination/source lifetime, invulnerability expiry, kamikaze timer/death continuation and owner release must survive saving and restoration. Merely selecting product missionpack enables PM_Weapon tags but supplies none of these effects.

Q3SelectedArsenal's existing checkpoint can carry current holdable/persistent tags, but pending world actors/timers and mine state require tagged saved records and readers. runtime.ts selectedBallistics capture/restore currently covers base projectiles and weapon statistics. Restore must resolve all actors before rebinding callbacks once; release must cancel links/triggers/timers. Campaign travel must distinguish transferable equipment from map-local mines/portals. Presentation/event additions must be reflected in simulation/types.ts, network/unified-event-codec.ts and consumers rather than emitting unknown event variants. This is a real scope obligation, not a proposal to edit every listed file immediately.

## Recommended sequence and acceptance boundary

Implement the resolved-supply-profile unit first: Team Arena map pickups into Q1/Q2 selected arsenals, with native holdables kept under the existing source owner. Verify expansion ammo/weapon grant, weapon-stay/dropped pickup, full capacity/rejection, auto-switch, respawn, console grant and save/restore. Keep persistent-ammo regeneration explicit as the next source-effects adapter if it is not included; do not describe the supply-only unit as complete expansion interchangeability.

Then independently close shared Team Arena ballistics with full proximity lifecycle and state restoration. Follow with foreign holdable/persistent services and product-correct construction/loadouts. Only then remove the foreign Team Arena arsenal guard and the same-family Q3 product restriction. Test Q1 and Q2 worlds plus baseq3/missionpack cross-product source, foreign characters/movement, death/respawn, release, save/load, travel and replicated event decoding. No new discovery/catalog system is required, and no UI defaults owner overlap is needed.
