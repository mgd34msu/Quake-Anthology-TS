### T1-001 — QuakeWorld programs played locally never run PlayerPostThink, so weapons cannot fire, and the test passes anyway
- **Verification (VERIFY-Q): confirmed. Final severity: High.** QW/server/sv_user.c:1520-1527 runs PlayerPostThink in SV_PostRunCmd, and up/Quake/qw-qc/client.qc:1183 calls W_WeaponFrame from it, so skipping it stops all firing. Source review: SRCQ1
- Severity: High
- Category: bug
- Location: src/app/bootstrap/simulation/runtime.ts:4092-4103,4999,5556; src/app/bootstrap/simulation/network-qw.ts:216; tests/first-playable/application/qw-local-play.test.ts:8-10,23-28; application/qw-ctf-rules.test.ts:93-94
- Confidence: reproduced (symptom), traced (cause)
- Evidence: the test comment says "QuakeWorld programs play in a local graphical session like every other source". The test holds fire for 20 frames, then asserts only `expect(ui().health).toBeGreaterThan(0)`.
  An instrumented copy (`t1/x/fire2.test.ts`, `fire3.test.ts`) used `--game q1-quakeworld --map dm3 --mode deathmatch` with mouse 1 held for 120 frames at 25 ms:
  - the binding was `+attack`, focus was `game`, `attack.active` was true and built commands had `buttons=[1]`
  - statement-profile counters stayed at `W_Attack` 0→0 and `W_FireShotgun` 0→0
  - shells stayed at 25→25, and the same held after a 5 s settle
  - `fire3` measured `PlayerPostThink` at 0 while `PlayerPreThink` went 1440→4320 and forward input moved the player 240 units

  Control: `q1-classic-id1` with TS Q1 and `--movement qw` went from 25 to 19 shells.

  The QC call sites explain this. `clientPostThink` for QW runs only at runtime.ts:4999, inside `runQuakeWorldCommands`. That queue is fed only by `queueQuakeWorldCommands`, whose only caller is network-qw.ts:216. The local-seat binding at runtime.ts:4092-4103 defines `beforePhysics` and no post-think.
- Impact: local QuakeWorld is offered through normal launch and is not playable as a shooter. QuakeC `PlayerPostThink` does not run, and in stock QuakeWorld that is the function that calls `W_WeaponFrame` and the power-up checks. Impulses and any other post-think state are lost too. qw-local-play and qw-expansions pass, and qw-ctf-rules passes because it teleports and never fires.
- Remediation: run the source post-think for local-seat QW commands, or route local seats through the QW command queue. Assert ammo decrease in the test.

### T1-003 — Split-screen remote client throws "Application content is closed" on a same-map reload after a seat drop and rejoin; the test covering it is red at HEAD
- **Verification (VERIFY-K): confirmed-with-changes. Final severity: Medium.** Real product bug, but intermittent (4 of 13 test runs) and needs a promoted primary seat, so reach is narrow. The order is the reverse of T1's, and T1's fix only turns the throw into a seat with no view. See "T1-003 detail" above; remote-application.ts:270,1179,1971,2038.
- Severity: High
- Category: bug
- Location: tests/first-playable/remote-application/application.test.ts:85-91,112-114; src/app/bootstrap/remote-application.ts:1212,1968,2030-2033,2038,2113
- Confidence: reproduced (symptom, three separate runs), traced (cause)
- Evidence: the unmodified test fails after exactly 33 `expect()` calls, which places it after the first `map base2` and inside the second one (line 112). It failed the same way in the earlier rerun (`test-rerun.log:1731`). It uses `--renderer cpu`, so it is not a GL-environment failure. The stack is `step → prepareRemoteSeatFrames → bindRemoteSeat → RemoteSeatView.prepare → loadWorld → provider → forContent`.
  Reduced in `t1/x/seq.test.ts`:

  | Scenario | Result |
  | --- | --- |
  | 1 seat, map sequence base2, base2, base1, base1 | all travel completes |
  | 2 seats, same sequence, no drop | all travel completes |
  | 2 seats, `local_drop` of the primary, `local_join`, base2 | completes |
  | same, then base2 again | `THROW Error: Application content is closed` |

  Likely cause: for non-unified sources `peerWorldCurrent` checks only `peer.map === this.options.map` (2030-2031), which stays true on a same-map reload. `loadServerWorld` closes the old content (1212), and `bindRemoteSeat` then passes `peer.loadedContent` (2038) before that peer's own load has refreshed it (1968). Without the drop the order evidently happens to work, so this is an ordering race.
- Impact: the exception leaves `step`, and under APP-001 that ends the client. The trigger needs split-screen on a remote server plus a seat drop and rejoin followed by a same-map server restart.
- Remediation: treat a peer as current only when `peer.loadedContent === this.loadedContent` for every source kind, as the unified branch already does.
