# Quake III comparison and shared-engine decisions

Audit date: 2026-09-12. Donor: `/home/buzzkill/Projects/quake-3-ts`. Unified engine: this repository. The [Q3 feature inventory](../verification/features/q3.json) records donor revision `8453c49824eb7a5ed5aee452f74e19336965d1f8` and 104 requirements. Its `sourceStatus` describes the donor; `targetStatus: required` is a requirement, not an acceptance result. The appendix preserves every Q3 ID without changing the larger feature inventory.

The intended result is one engine with the strongest useful capabilities from every family. Q3 does not win an overlapping subsystem merely because it is newer. The existing common frame, actor identity, combat authority, scene, and device ownership are the foundation for composition. Several source algorithms still run separately behind those interfaces; sharing an API does not establish that their implementations have been consolidated.

The Shambler damage change is committed and pushed as `0d4d3c4da3a0814edb8103307cc35fe2e399511a`; the writer reports strict/policy checks passed and root verified 14 tests with 198 assertions across the actual fixture and authority suite. The installed executable remains at `e20b6d68`, so these source results do not describe that installed binary.

This is a source audit with bounded execution evidence identified below. Referenced tests that were not run for this audit are verification targets, not passing claims. No native game, device, platform release, image-parity, or performance comparison was run. Choices lacking those comparisons are provisional.

## What remains before claiming the Q3 feature union

The largest concrete joins still needed are Q3 world saves; executable QVM/native mod selection; native demo application flow; progression and menu flows; and foreign-map objectives with team bot bindings. Existing separate audio algorithms need consolidation into one scalable core. Multi-seat input, presentation, prediction and audio must replace donor single-client assumptions. Partial donor services and missing donor capabilities remain requirements; copying the donor cannot close them.

Acceptance should use actual supported maps and common actors, committed outcomes, fresh-process saves, network peers, and rendered/device output appropriate to each claim. Synthetic objective and codec tests remain useful for local semantics, but they cannot substitute for those application witnesses. Fidelity and performance comparisons are still needed to turn provisional renderer/audio choices into measured decisions.
