# Source-backed reuse contracts

This W01 artifact selects starting mechanisms for consolidation. It does not accept imported code or establish runtime fidelity. The [source assessment](source-assessment.md) and [project plan](project-plan.md) define the scope. The [W01 source census](../verification/source-manifest.json) owns repository revisions and individual file hashes. Source IDs below refer to its repositories, including `q1-ironwail` for enhanced Q1 behavior and `q2-repro` for Q2 rerelease engine behavior.

Three evidence labels apply throughout this document:

- **Source comparison** means the cited TypeScript and original implementation bodies were inspected in this run. It establishes a control-flow or representation difference without establishing the behavior of a built original binary.
- **Donor execution** means an explicitly described TypeScript probe ran in this run. Agreement between ports is not an independent fidelity oracle.
- **Required proof** describes acceptance work that has not run here. No rendering, audio, network peer, campaign, or save restoration was executed for this artifact.

Lineage identifies candidates. It does not establish semantic equality. Each selected mechanism still needs strict TypeScript migration, session ownership, and the proofs described below.

## RC01 Math and numeric behavior

Source comparison: Q1 [mathlib.ts](/home/buzzkill/Projects/quake-1-re-ts/src/common/mathlib.ts) and Q2 [math.ts](/home/buzzkill/Projects/quake-2-re-ts/src/shared/math.ts) store vectors in `Float32Array`, but their `DotProduct` accumulates products as JavaScript numbers. Vector stores round while many intermediate scalar expressions do not. Q3 [math.ts](/home/buzzkill/Projects/quake-3-ts/src/core/math.ts) uses readonly coordinate records and `vec3` rounds each component. Its `dot3` rounds each product and ordered addition. Its [qvm-math.ts](/home/buzzkill/Projects/quake-3-ts/src/core/qvm-math.ts) distinguishes QVM `AngleMod` and constant folding from the general math implementation.

The original [Q1 math header](/home/buzzkill/Projects/qsrc/quake/WinQuake/mathlib.h), [Q2 math header](/home/buzzkill/Projects/qsrc/quake-2/game/q_shared.h), and [Q3 math header](/home/buzzkill/Projects/qsrc/quake-iii-arena/code/game/q_shared.h) contain similar `DotProduct` expressions. That text does not select the compiler, intermediate precision, VM instructions, or guest floating-point environment. Q3's [numeric.ts](/home/buzzkill/Projects/quake-3-ts/src/core/numeric.ts) explicitly makes `qvmFloatToInt` consume binary32 and return `INT_MIN` for NaN or out-of-range input. A JavaScript bitwise conversion would instead apply JavaScript wrapping rules.

Donor execution: the real imported `DotProduct` functions returned `1` for Q1 and Q2, while Q3 `dot3` returned `0`, for the dot product of `[16777216, 1, -16777216]` and `[1, 1, 1]`. This proves a donor disagreement, not which numeric profile is authoritative. The probe is reproducible from the destination root:

```sh
bun -e 'import { DotProduct as q1dot, vec3 as q1vec } from "../quake-1-re-ts/src/common/mathlib.ts"; import { DotProduct as q2dot, vec3 as q2vec } from "../quake-2-re-ts/src/shared/math.ts"; import { dot3, vec3 } from "../quake-3-ts/src/core/math.ts"; const result = { q1: q1dot(q1vec(16777216, 1, -16777216), q1vec(1, 1, 1)), q2: q2dot(q2vec(16777216, 1, -16777216), q2vec(1, 1, 1)), q3: dot3(vec3(16777216, 1, -16777216), vec3(1, 1, 1)) }; if (result.q1 !== 1 || result.q2 !== 1 || result.q3 !== 0) throw new Error("Numeric donor observation changed"); process.stdout.write(JSON.stringify(result) + "\n");'
```

Selection: reuse Q3's explicit operations and types as the implementation pattern. The recipe selects numeric profiles independently of protocol and renderer. A helper shared across profiles must have the same operation sequence, rounding points, integer conversions, and alias behavior. Q1/Q2 mutable output routines and guest memory writes cannot be replaced by copied readonly vectors where callers observe in-place mutation.

Required repairs and invariants:

- Every movement, trace, damage, RNG, and prediction chain identifies its arithmetic profile and preserves evaluation order. Final-coordinate rounding is insufficient.
- Integer wrapping, valid conversions, and source undefined conversions remain different operations. Native x87, SSE, and QVM profiles cannot be inferred solely from the source language.
- Q1 `Q_rand` currently uses `Math.random` when unseeded and xorshift when seeded. Those are port additions, as the inspected body confirms. They cannot be accepted as the original C library `rand` algorithm. Q3 `qRand` explicitly uses `69069 * seed + 1`. RNG state and draw order belong to their selected owner and checkpoint.
- Required proof includes bit-pattern traces across contacts and predictable events, zero and signed-zero behavior, conversion boundaries, aliasing, and restored RNG continuation against the applicable independent reference.

## RC02 Commands

Source comparison: Q1 [cmd.ts](/home/buzzkill/Projects/quake-1-re-ts/src/common/cmd.ts) prepends aliases and registrations, matching [WinQuake cmd.c](/home/buzzkill/Projects/qsrc/quake/WinQuake/cmd.c). `Cbuf_InsertText` adds a newline only for the QW console profile, matching the difference in [QW cmd.c](/home/buzzkill/Projects/qsrc/quake/QW/client/cmd.c). The Q1 donor also adds a final newline in `Cmd_Exec_f` for files missing one. That useful file-loading repair is distinct from changing all NetQuake insertion semantics.

Q2 [cmd.ts](/home/buzzkill/Projects/quake-2-re-ts/src/qcommon/cmd.ts) uses insertion-ordered `Map` objects for commands and aliases. The original [Q2 cmd.c](/home/buzzkill/Projects/qsrc/quake-2/qcommon/cmd.c) prepends list entries. Completion and listings can therefore choose a different first match. Both Q2 implementations put aliases before cvars and limit alias expansion through `ALIAS_LOOP_COUNT`.

Q3 [commands.ts](/home/buzzkill/Projects/quake-3-ts/src/core/commands.ts) uses `CommandBuffer`, prepends registrations, and moves a dispatched registration to the head. The original [Q3 cmd.c](/home/buzzkill/Projects/qsrc/quake-iii-arena/code/qcommon/cmd.c), `Cmd_ExecuteString`, does the same. Its fallback order is cvar, client game, server game, UI, then server forwarding. Q3 registers `vstr` and numeric `wait`; Q1/Q2 retain their alias and one-drain wait behavior. The Q3 buffer also offers async execution, which is unsuitable for ordering simulation commands.

Selection: consolidate storage ownership, byte bounds, registration bookkeeping, and synchronous dispatch from Q3. Keep explicit command dialects and dispatch contexts. Alias evaluation and Q2's deferred command buffer are retained capabilities. A frame drain owns its source, profile, session, and seat across inserted text and `wait`; the Q1 donor's process-wide buffer/profile switching is replaced.

Required invariants: preserve quoted semicolon splitting, comments, token byte limits, NUL handling, macro/alias expansion, duplicate registration outcomes, completion order, and overflow behavior per dialect. A command cannot execute with another seat's context after waiting. A registered null callback follows the source fallback behavior. Nested commands complete before their parent returns. Required proof includes case-colliding registrations, aliases that insert commands, a file without a terminal newline, overflow boundaries, and two independent buffers drained in alternating order.

## RC03 Cvars

Source comparison: Q1 [cvar.ts](/home/buzzkill/Projects/quake-1-re-ts/src/common/cvar.ts), `Cvar_FindVar`, compares exact names and preserves a newest-first linked list, matching [WinQuake cvar.c](/home/buzzkill/Projects/qsrc/quake/WinQuake/cvar.c). Its QW `info` propagation can target the client or server separately. The original [QW cvar.c](/home/buzzkill/Projects/qsrc/quake/QW/client/cvar.c) selects those sides at compile time. This distinction is useful for a process containing both endpoints.

Q2 [cvar.ts](/home/buzzkill/Projects/quake-2-re-ts/src/qcommon/cvar.ts) also uses exact names, but its `Map` enumerates oldest-first. The original [Q2 cvar.c](/home/buzzkill/Projects/qsrc/quake-2/qcommon/cvar.c), `Cvar_Get`, prepends. `Cvar_Set2` distinguishes forced writes, write protection, and latched values. Applying the latched `game` cvar also changes mounts and executes configuration. Enumeration order therefore cannot be dismissed merely because each cvar is visited once.

Q3 [cvar.ts](/home/buzzkill/Projects/quake-3-ts/src/core/cvar.ts), `CvarRegistry`, uses ASCII case-insensitive name keys, modification counts, VM mirrors, defaults, flags, and latched strings. The original [Q3 cvar.c](/home/buzzkill/Projects/qsrc/quake-iii-arena/code/qcommon/cvar.c), `Cvar_FindVar`, uses `Q_stricmp`. Q3 numeric parsing and `setValueText` also explicitly model binary32 storage and C-style formatting. These semantics do not match Q1 `Q_atof` or Q2's current `parseFloat` helper automatically.

Selection: reuse registry ownership and versioned VM synchronization. Keep dialect-specific identity, parsing, formatting, flags, latching, and info propagation. Preserve Q1 declaration defaults and separate QW client/server info outputs. Repair Q2 enumeration to match the selected original when order is observable. Replace global filesystem side effects with a resolved, ordered transition operation at the application boundary.

Required invariants: a Q1/Q2 name differing only in case can remain distinct; a Q3 name follows ASCII case-insensitive lookup. Equal-string writes, forced writes, flags, default values, modification counts, and info serialization retain source behavior. Server state and seat configuration have separate owners. Required proof covers restart with latched values, VM mirror refresh, registration collisions, text-number conversion, and exact emitted configuration/info bytes.

## RC05 Network bytes and bit encoding

Source comparison: the Q1 [sizebuf.ts](/home/buzzkill/Projects/quake-1-re-ts/src/common/sizebuf.ts) and original [WinQuake common.c](/home/buzzkill/Projects/qsrc/quake/WinQuake/common.c) implement `MSG_WriteAngle` by truncating the angle before scaling. Q2 [sizebuf.ts](/home/buzzkill/Projects/quake-2-re-ts/src/qcommon/sizebuf.ts) and original [Q2 common.c](/home/buzzkill/Projects/qsrc/quake-2/qcommon/common.c) scale before truncating. For `1.9` degrees, the source expressions select byte `0` for Q1 and byte `1` for Q2. This is a source-derived witness, not a packet captured from an original engine.

Q1 enhanced `MSG_WriteCoordFlags` and `MSG_WriteAngleFlags` use `Q_rint`, float, or wider coordinate encodings according to negotiated flags, matching the inspected [Ironwail common.c](/home/buzzkill/Projects/qsrc/ironwail/Quake/common.c). Classic Q1/Q2 fixed coordinates truncate `f * 8`. Enhanced defaults cannot replace those classic encoders.

Q3 [message.ts](/home/buzzkill/Projects/quake-3-ts/src/protocol/message.ts), `MessageWriter.writeBits`, uses raw low bits plus Huffman-coded bytes in bitstream mode, and little-endian scalars in OOB mode. Original [Q3 msg.c](/home/buzzkill/Projects/qsrc/quake-iii-arena/code/qcommon/msg.c) also checks a four-byte reserve before scalar writes and advances the OOB writer's bit counter by eight for a 32-bit long. This odd counter behavior is source-specific; it does not justify a universal counter implementation.

Q2 [q2repro.ts](/home/buzzkill/Projects/quake-2-re-ts/src/qcommon/protocol/q2repro.ts) distinguishes protocol `1038` from the engine-private `4038`. Its batch movement code retains classic vertical movement and light level only under `4038`. The reference [q2repro protocol header](/home/buzzkill/Projects/qsrc/q2repro/inc/common/protocol.h) identifies rerelease `1038`; private `4038` cannot inherit independent interoperability from that reference.

Selection: share bounded byte storage, endian reads, and reusable compression algorithms where their contracts agree. Keep explicit codec variants for message layout, delta fields, signedness, quantization, capacities, framing, reliable state, and protocol version. A codec reports whether it can represent a resolved session. Mixing actors does not authorize silent truncation into an older entity or inventory format.

Required invariants: preserve exact bytes, read cursors, overflow state, sentinel/error results, string filtering, changed-field bits, and command history. Angle quantization is a wire rule separate from simulation math. Required proof covers negative/fractional coordinates, `1.9` degrees, signed bit widths, malformed/truncated packets, delta omissions, reliable replay, and independent reference peers for each claimed original protocol. Two endpoints from this engine prove only local agreement.

## RC06 Entity allocation, deletion, and identity

Source comparison: Q1 [pr_edict_core.ts](/home/buzzkill/Projects/quake-1-re-ts/src/progs/pr_edict_core.ts), `ED_Alloc` and `ED_Free`, preserves the original [pr_edict.c](/home/buzzkill/Projects/qsrc/quake/WinQuake/pr_edict.c) allocation condition `freetime < 2 || time - freetime > 0.5`. Freeing clears selected fields, marks the slot free, and sets `nextthink = -1`. It does not zero every field or clear all references to that slot.

Q2 [g_utils.ts](/home/buzzkill/Projects/quake-2-re-ts/src/game/g_utils.ts), `G_Spawn` and `G_FreeEdict`, follows the same ordinary half-second reuse condition, but its free path clears the entity after unlinking. The original [Q2 g_utils.c](/home/buzzkill/Projects/qsrc/quake-2/game/g_utils.c) also exempts slots at or below `maxclients + BODY_QUEUE_SIZE` from that clear, after unlinking them.

Q3 [entities.ts](/home/buzzkill/Projects/quake-3-ts/src/game/entities.ts) owns its pool, preserves object identity at a slot, and rejects objects from another pool. Its ordinary reuse condition matches [Q3 g_utils.c](/home/buzzkill/Projects/qsrc/quake-iii-arena/code/game/g_utils.c): skip a free slot when its free time is after `startTime + 2000` and elapsed time is less than `1000`. `neverFree` entities are unlinked before the free path returns. The original checks `MAX_GENTITIES` and `ENTITYNUM_MAX_NORMAL` at different points; the source's apparently forced reuse loop is not permission to change the port's exhaustion behavior without analysis.

Selection: reuse Q3 ownership checks and instance construction as patterns, then implement the plan's shared generational registry. Do not promote Q3's existing stable slot objects to the universal actor identity. Built-in shared operations use generation-checked identities. Source API/guest views separately model stable slots, pointers, field retention, and reuse. A stale guest pointer may observe a reused slot where the original does, while a stale shared actor identity must never acquire authority over its replacement.

Required invariants: source allocation order, startup grace periods, boundary inequalities, reserved slots, partial versus full clear, unlink-before-free, and callback-visible reuse remain explicit. Required proof includes exact cooldown boundaries, deletion during nested callbacks, allocation in the deleted slot, two sessions with the same slot number, pool exhaustion, and fresh-process restoration of guest-visible identities.
