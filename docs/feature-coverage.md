# Unified feature coverage

This ledger preserves the union of player, server, and runtime functionality identified in the Q1, Q2, and Q3 source assessments. It is a planning artifact, not a certification. No tests or game sessions ran for this document. The source revisions are pinned in [source-assessment.md](source-assessment.md).

All requested runtime and game features remain mandatory for complete single-player and multiplayer support. A missing or partial donor creates implementation work. It does not remove the feature from the target. Splitscreen is one example among these obligations.

`I` means inspected implementation exists, without fresh correctness verification. `P` means partial implementation or identified limits. `T` means intended target behavior with no complete donor identified. The source-family IDs retain all 40 inventory entries: Q1F01–Q1F11, Q2F01–Q2F13, and Q3F01–Q3F16. F01–F25 identify the unified rows for the dependency graph.

This is a feature-family ledger, not a claim that every command, cvar, callback, or menu action has been enumerated. P0 expands each row into source-backed feature records and accounts for every relevant source function and exposed workflow. No function disappears merely because its family already has a row. Individual records carry original-source authority, selected implementation, dependencies, and acceptance evidence. [verification-plan.md](verification-plan.md) defines the evidence standard.

Owning package IDs refer to the work packages from the initial build plan (the machine work graph was retired after the build; IDs are retained here as stable references). W01 performs the shared feature/source census; W02–W04 establish original baselines and enforce verification. W64–W72 supply cross-cutting gameplay, integration, configuration-matrix, performance, release, and independent-review gates. W74 extracts permanent source-derived behavior, and W73 proves the first actual mixed-game executable, including CPU/GL, saves, progression, and coop, before bulk content work. The row owners below identify implementation responsibility without duplicating those shared gates. Every row remains planned until its acceptance evidence exists.

Source-family IDs identify the inventory records contributing to each row; the linked locations identify concrete implementation evidence. A family association does not assert that its donor supplies every requirement in that row.

## Component selection

Choose the best demonstrated component for each contract. Q3's stronger policy, explicit ownership, rendering interfaces, and verification infrastructure make it a preferred starting point in those areas. That preference is conditional, not a repository-wide ranking. Equivalent or better Q1/Q2 implementations remain reuse candidates.

Q1 contributes content/program separation, QuakeC host profiles, navigation knowledge, rerelease text, controller/haptics, and local-player work. Q2 contributes content/map-source precedence, MD5 replacement scale, BSPX lighting, campaign transitions, guidance/HUD, seat handling, environmental audio, downloads, and server browsing. Q3 contributes material/render ownership, QVM execution, arena objectives, team AI, policy enforcement, and snapshot-based checks. Source overlap should reduce duplicate code after semantic comparison; shared names alone do not prove equivalent behavior.

Donor tests become candidate acceptance cases, not automatic passes. Current original-source behavior, real content, and combined execution decide which implementation is retained. Partial wheel, subtitle, achievement, lobby, save, bot, or UI paths remain named work until complete.
